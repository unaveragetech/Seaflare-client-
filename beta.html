Client core

Stable

Everything in Seaflare Market registers through one client entrypoint that hooks Fabric's tick events. On every client tick it polls the movement-safety checks, drives the module manager (which in turn ticks every enabled module and the ESP scanner), polls for a runtime-bound keybind, and — every other tick — advances the RTP mapper and folds in any freshly written RTP samples. A separate config system persists every setting to disk keyed by module id, so a restart never quietly resets a tuned value back to default.

How state survives a restart

Nothing is held only in memory. HUD layout, module settings, the RTP mapper's rotation cursor and sample store, auction data, and the trade order queue all round-trip through JSON files in a dedicated data directory. The client reads them back on the next launch before anything else runs, so a mid-run crash costs at most the current in-flight action — never the accumulated state around it.

Auction House Suite

Stable

The AH tooling is split into two halves that don't trust each other's assumptions: a repository layer that scrapes and caches market data, and a trade layer that physically assembles and lists a sell lot through real inventory clicks. The two only talk through plain data — the trade layer never has to know where a price came from, and the repository never has to know how a listing gets placed.

Why every click is verified

Early builds of the sell-lot assembler trusted a boolean return from the inventory-click bridge as proof a click had landed — it only proved the click was dispatched without throwing, which vanilla essentially never does regardless of whether anything actually moved. The current version re-reads the real slot and cursor state after every click, polls for up to several hundred milliseconds if the expected state hasn't appeared yet (clicks on a real remote server land with real network latency, not instantly), and retries the exact click a bounded number of times before giving up loudly with a precise reason — which slot, which step, what it found instead of what it wanted.

What the order queue does

A standing sell or buy rule doesn't fire once and forget. It re-evaluates on its own schedule, logs why an attempt failed when one does, and — because the assembly step is verified — never reports a listing as placed when the inventory says otherwise. Webhook alerts fire from the same evaluation path, so a notification and a real state change are never out of sync with each other.

RTP Mapper

Stable

The mapper treats DonutSMP's /rtp command as a sampling instrument rather than a slot machine. It walks the enabled regions in round-robin order, fires one sample per cooldown window, and records every landing — position, region, and whether it matches whatever search criteria are currently armed.

Cooldown auto-backoff

The server's real /rtp cooldown isn't published anywhere — it just silently ignores an early request with no chat message and no error. Rather than hardcode a guessed delay, each consecutive miss doubles a backoff added on top of the configured floor, and a landed sample clears it. The rotation self-tunes toward whatever the server is actually enforcing instead of the value slowly drifting wrong as the server's own limits change.

Cluster detection and stop-rule search

DonutSMP tends to re-drop players into a surprisingly small set of spots per region. Repeat-area detection compares each new landing against everything already recorded for that region, and once a region stops producing new ground it rotates away early instead of burning its whole sample budget re-mapping the same coordinates. Layered on top of that, a criteria search evaluates every fresh landing against rules you set — distance from spawn, biome, whatever matters for the base or mine you're hunting for — and halts the whole run the moment one matches, rather than mapping indefinitely.

The overlay that survives a teleport

An /rtp makes the game replace whatever screen is open with the terrain-loading screen — this happens on every single sample, and nothing in the mapper's own tick was ever the cause of it closing. The client watches for that and reopens the same map instance (not a fresh one) once the world settles, which is what keeps pan, zoom, and colour mode intact across a run instead of resetting the view every teleport.

Backtrack Home: /sethome and /delhome as a bookmark

When "Save landing as home" is on, every confirmed landing runs a two-command sequence: /delhome mapper to clear the previous bookmark, then - deferred to a later client tick rather than fired in the same one, since DonutSMP needs a moment to actually free the slot before it can be reclaimed - /sethome mapper to claim the new landing. The deferred half runs ahead of the mapper's own enabled check specifically so that a run which disables itself the instant it lands - a stop-rule match, most commonly - still finishes saving the bookmark rather than dropping it because the run technically ended first. "Go Home" on the main screen, and any other code that wants the same backtrack, both go through one shared method rather than duplicating the command string. Off by default: DonutSMP gives 3 home slots, and spending one is the player's call.

HUD & module system

Stable

Every on-screen HUD element and every module shares one settings model: a typed setting object with a label, help text, bounds, and persisted value, rendered generically by whichever screen is showing it. That's what makes "every panel opens into real settings" true rather than aspirational — a HUD component with no tunables still gets an enable switch and a note saying so, instead of an empty box that looks broken.

Keybinding, the way modern clients do it

Middle-click a module and the row switches to "press a key" — the next key or mouse button becomes the bind, Escape or a left-click cancels, Delete clears it. Modifier keys alone don't end the watch, since almost every real bind is pressed on the way through a modifier. This replaced an earlier "hover a row and press any key" scheme, which meant a stray keystroke while your mouse happened to be sitting over a module silently rebound it.

Settings windows that scroll and verify

A settings window sizes itself to how many settings the module actually has rather than a fixed box, clips its content instead of painting over its own header, and — for numeric settings — offers both a drag bar and a typable value box with the input clamped to the setting's real range. Text fields accept full paste and every printable character, which sounds trivial until the alternative is a webhook URL you can't actually type because a period wasn't on an old character whitelist.

Automation safety net

Stable

Panic Mode, Auto Log, and Auto Relog exist because unattended automation needs an exit condition, not just a start condition. Panic Mode disables every module, the RTP mapper, and every enabled module in the bundled Seaflare client in one pass, and restores exactly what it disabled on release — nothing is left toggled off that was on before, and nothing extra gets re-enabled.

Why relog can't live inside a module

A module's tick loop stops running the instant the world goes null, which is exactly the state a reconnect spends almost its entire life in — so a module can start a logout but can never be the thing that finishes it. Session control for Auto Relog runs from the raw client tick instead, holding the target server address in a static field because the game clears its current-server entry as part of disconnecting, and it cancels itself cleanly if you rejoin by hand before the timer fires.

Grace windows against retrigger loops

Both trigger modules ignore every condition for a configurable window after a fresh world is entered. Without it, a condition that's still true the moment you rejoin — low health, a player still standing nearby — fires again instantly, and Auto Relog turns into a join/quit loop instead of a safety net.

Minescript bridge

Stable

Minescript is the scripting layer every AH and RTP action is actually written against — the Java client exposes a small set of container-interaction primitives (click a slot, read a slot, read the cursor) through Minescript's Java-interop API, and the Python side orchestrates those primitives into the higher-level flows: assemble a sell lot, list it, sample an /rtp, tend a chat command.

The click bridge, and the lesson learned from it

The bridge dispatches through the same code path a real mouse click uses — the vanilla screen-handler click method — rather than forging a network packet, so the server sees an ordinary player action. What it does not do on its own is confirm that action landed: the underlying call reports success as soon as it doesn't throw, which vanilla rarely does regardless of outcome. Every call site above it is responsible for re-reading real state afterward, which is the pattern documented in the Auction House section above and now applied everywhere the bridge is used.

Humanized pacing

Every scripted delay runs through one jitter function so no two actions share an identical cadence, with a single speed knob that scales every wait in a run together rather than needing each call site tuned separately. Timing that looks the same every single time is itself a signal — the jitter exists so the automation reads as organic input, not a fixed macro loop.

Allegro pathfinder

Beta

Allegro is this project's own pathfinding engine, written from scratch against the Minescript API rather than wrapping an existing pathfinder — the goal is white-room parity with modern Baritone from a different angle: fully humanized movement (jittered timing, eased camera turns with subtle wobble, occasional pauses) instead of Baritone's direct input-simulation approach, and a client that never locks the player out of control while it runs.

Configuration compatibility, honestly scoped

Every one of Baritone's 247 known settings is accepted by Allegro's own config command, so a Baritone-tuned settings file drops in without translation. As of this page, 36 of those settings are wired into real, load-bearing behavior — vanilla-accurate movement costs, avoid/throwaway lists, break timeouts among them — and the remainder are accepted and persisted for when their behavior is ported, rather than silently discarded. The project's own parity tracker enumerates every setting, movement type, and goal against its current status rather than claiming full coverage it doesn't have yet.

Belfegor (bundled, not authored by this project)

Bundled · Unmodified

Belfegor is a separate autonomous-bot mod — smart crafting, advanced PvP, and general task automation — authored by beelzebub4883 and published at github.com/unaveragetech/belfegor. Seaflare Market bundles it as a jar-in-jar dependency, embedded completely unmodified, alongside the specific Baritone runtime version it requires to function (also embedded unmodified) so that installing Seaflare Market is enough on its own — nothing extra needs to be downloaded or configured for Belfegor to load and run.

What "bundled" actually means here

This is the same honesty standard applied to the bundled Seaflare (LiquidBounce) build: Belfegor is not called into, wrapped, or referenced anywhere in Seaflare Market's own Java or Python source. It ships as its own independent mod with its own entrypoint and its own in-game presence, running side by side with everything documented on this page rather than underneath it. If you never open Belfegor's own interface, it sits idle — none of the Auction House, RTP Mapper, HUD, or safety-net systems described above depend on it in any way, and none of them call into it.

Why it's here at all

Belfegor is the same author's other project, and bundling it turns Seaflare Market into a single install that also covers autonomous crafting and PvP automation for players who want that on top of the market and mapping tooling — without asking anyone to track down and install a second mod, and without this project's own code needing to reimplement what Belfegor already does well.

Bundled Seaflare

Stable

Seaflare is a rebranded build of LiquidBounce — every modification made to it is cosmetic: name, artwork, the title-screen background, and the menu accent colour. No feature was added, removed, or reimplemented, and no click, keybind, or menu still calls anything other than exactly what it called upstream. That distinction matters under GPL-3.0: it's what lets this project describe precisely, rather than vaguely, what changed and what didn't.

Why reflection, not a hard dependency

Seaflare Market talks to the bundled Seaflare client entirely through reflection — resolving its classes and methods by name at runtime rather than compiling directly against them. That means the market and mapping tooling still builds and runs even if a future Seaflare build renames something internally: the bridge reports itself unavailable instead of crashing the whole client, and everything that doesn't depend on Seaflare keeps working.
